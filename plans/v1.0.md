## My defaults (say if you want any changed)
- **Backfill baseline:** your first 50 eligible analyzed games, in order played. That's what a first Coach run at the default settings would see, and it doesn't depend on whatever filters an old report used. A weakness first seen later gets its baseline at the checkpoint where it first appears.
- **Backfill rules:**
  - One point per 10 eligible games after the baseline window, each over the rolling 30-game window.
  - Puzzle accuracy for Fixed comes from local attempts dated before that point. The Lichess dashboard is only "now", so the backfill doesn't use it.
  - Points are marked *reconstructed*: they appear in charts and history but save **no Coach report** (otherwise dozens would flood the report list).
  - The Suggested mix is rebuilt once at the end, through the usual banner (FR-10.31).
- **Status-change notification (FR-10.38):** an in-app notice plus an entry in the checkpoint history; on by default. No Windows toast, which would need a new dependency.
- **Wizard trigger:** only on a fresh install, i.e. no `puzzles.db` and the wizard not finished. Your current install never sees it.
- **`setup.wizard_done` is a PC-only setting** (added to `PC_LOCAL_KEYS`). After a restore from the wizard, the app restarts back into the wizard at the puzzle-DB step.
- **Checkpoint game filters:** rated, rapid + classical, both colors (FR-10.4 defaults), stored as checkpoint settings separate from the Coach page's last-run filters. Only your linked accounts count, never "another player".

  - One checkpoint at a time; a trigger while one runs is dropped.

  - order: Regressed first, then New/Training by score, then Improving
  - Fixed weaknesses get a 10% maintenance share

- [x] Bridge (`@bridge_call`, allowlist test updated in the same commit): `get_progress`, `get_checkpoint_settings`, `set_checkpoint_settings`, `run_checkpoint_now`, `take_status_notices`. (`checkpoint_ai_take` moved to v1.0c with the AI summary it serves.)

**v1.0a landed (2026-11-10):**
- **Guard rule changed (Adam, during the build):** guarded = fewer than 5 occurrences *and* a baseline that expected
  fewer than 5. The literal FR-10.34 ("expected at least 5") would have guarded every real improvement, so nothing
  could become Fixed. REQUIREMENTS FR-10.34 updated.
- A whole-game weakness absent from a report isn't measured (no point, no change); a Missed / Allowed theme or a
  habit tag absent counts as zero (`absent_means_zero`).
- `CoachService._run` split into `_produce` / `_build`; `checkpoint_report` and `measure_games` reuse them. The first
  checkpoint's baselines come from `measure_games` on the last 50 eligible games, with no second report saved.
- When a window has nothing to build a mix from (all clean games), the previous Suggested mix stays.
- Version bumped to 1.0.0 now (`test_versions_agree` checks it against the branch), not in v1.0e.
- Tests: `tests/unit/test_fix_tracking.py` (49), `tests/unit/test_suggested_mix_statuses.py` (5),
  `tests/integration/test_checkpoints.py` (19). `tests/helpers.api_for` builds the bridge over existing services.

## v1.0b: Backfill (one-time)
- [x] A background job at the first launch after the migration, guarded by a `checkpoints.backfill_version` key (the same pattern as `game_puzzles.BACKFILL_KEY`). It reads stored `game_analysis` only, with no engine and no LLM, and replays the history as described under *My defaults*.
- [x] It's safe to interrupt (resumes next launch) and idempotent. It's skipped cleanly when there are fewer than 50 eligible analyzed games (the first real checkpoint sets the baseline instead).

**v1.0b landed (2026-11-10):**
- `CoachService.measure_stored`: stored analysis and tags only (no engine, no re-tag, no puzzles, no report).
- Points are dated by their newest game's `played_at`, so the charts follow when you played.
- No mix existed back then, so a backfilled weakness is New, not Training; the mix is rebuilt once at the end
  (`report_id` 0 in the suggestion, since there's no report).
- **Run checkpoint now** and the count trigger refuse while the backfill hasn't run; `start()` runs it first.
- Skipped when live checkpoints already exist (e.g. a restored newer backup).
- Tests: `tests/integration/test_checkpoint_backfill.py` (10).

## Tests (ROADMAP *Done when*, plus)
- **Status rules:** every FR-10.35 transition on synthetic data, including Fixed needing 2 consecutive checkpoints *and* the puzzle gate, puzzle accuracy alone never making Fixed, Regressed from Fixed and from Improving, and the guard blocking a change.
- **End-to-end checkpoint:** runs on recorded data, saves a report that shows under Since last report, and rebuilds the mix. Filters edited by hand get the banner instead.
- **Plan untouched:** a checkpoint leaves the plan tables byte-identical.
- **Triggers:**
  - count: fires at N, not N − 1
  - schedule: a due schedule runs while open (fake scheduler and clock) and at the next launch; due with no new games does nothing
  - another player's games never count
- **Backfill:**
  - point count and window contents on a fixture history
  - statuses match running the live rules checkpoint by checkpoint
  - no reports created
  - re-run adds nothing
  - interrupted then resumed gives the same result
  - fewer than 50 games is skipped
- **Suggested mix:** status ordering and the maintenance share.
- **AI summary:** auto only under cap and budget; otherwise it waits for Confirm. The prompt holds aggregates only, with no Advanced, notes or journal.
- **Progress page (Playwright):** hollow guarded points, the baseline line, chart titles saying lower is better, and the empty state.
- **Wizard:** fresh install → wizard; existing install → no wizard; restore from the wizard → restart → resumes at the puzzle-DB step; each step resumable.
- **Fresh clone:** QA clones into a temp folder with a temp data folder and goes from `setup.py` through the wizard, once fresh and once restoring a v0.16 backup. The clean-Windows-profile run is Adam's manual test.
